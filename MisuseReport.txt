HPC Incident Post-Mortem — bacass / funcscan runs, DTU HPC (Mar–Apr 2026)
===========================================================================

Summary
-------
Seven distinct incidents, several compounding each other: context-switch storms from mis-declared
CPU counts, NFS metadata hammering from an LD_PRELOAD open-retry library, BeeGFS write overhead
from Nextflow's built-in tracing, wrong LSF memory reservations, unnecessary rsync bursts from
scratch = true on database-heavy processes, a SPAdes stale checkpoint bug that triggered a costly
rerun, and sustained InfiniBand read pressure from the DeepBGC Pfam database in funcscan. All
have been resolved in the current configuration.


Incident 1 — Context-switch storm: FastQC (primary ban trigger)
----------------------------------------------------------------
What happened: FastQC was configured with cpus = 2. The Java Virtual Machine (JVM) ignores declared
CPU counts and spawns ~20 OS threads per instance regardless. With queueSize = 150 concurrent jobs
and 2 declared CPUs, LSF placed up to 10 FastQC jobs per 20-core node. Each node then ran ~200 JVM
threads simultaneously, generating 1.8 million context-switches per second. HPC administrators
observed this as nodes becoming unresponsive and killed the job.

Root cause: LSF schedules by declared CPUs, not actual thread footprint. FastQC's JVM doesn't
respect the Nextflow CPU allocation. The combination of many concurrent jobs + high thread-to-core
ratio caused kernel scheduler saturation.

Compounding factor: queueSize = 150 at the time (later reduced to 80 after HPC staff complaint)
allowed up to 1,500+ concurrent LSF slots, maximizing co-location of CPU-lying jobs on individual
nodes.

Fix: cpus = 8 for FastQC (so LSF places at most 2 jobs/node → ~40 threads), maxForks = 20 as an
additional concurrency cap. Same pattern applied to BUSCO (augustus spawns 100–500 short-lived child
processes per job) and SPAdes via maxForks = 15 on UNICYCLER with order[-slots] to encourage
spreading across nodes. queueSize reduced from 150 → 50 overall.


Incident 2 — NFS metadata storm: libnfs_retry.so (the C library)
-----------------------------------------------------------------
What happened: A C LD_PRELOAD library (bin/libnfs_retry.c) was introduced to handle intermittent
BeeGFS ENOENT failures when files existed but were momentarily unreadable. The library intercepts
every open(), open64(), openat(), openat64(), fopen(), and fopen64() call system-wide. Its logic:

    open(path) → ENOENT?
      → call stat(path)
         stat fails → genuine ENOENT → return immediately
         stat succeeds → spurious ENOENT → retry 5× (50ms × 3, 5s, 20s)

The fatal flaw: Python's module import mechanism probes every entry in sys.path for every possible
file extension (.py, .pyc, .so, /__init__.py, etc.) when importing a module. The vast majority of
these probes are intentional ENOENT — the file does not exist at that path. The library's stat()
discrimination check fires on every one of them.

A single conda environment activation generates hundreds to thousands of ENOENT probes across
sys.path. With 80 concurrent jobs starting simultaneously (e.g. FASTP, KRAKEN2, BAKTA all launching
at once), this produced a burst of thousands of stat() calls per second against the BeeGFS metadata
server — affecting not just this project but all users of the shared cluster filesystem.

Why it was hard to see: The library worked correctly in isolation (stat correctly discriminated real
vs spurious ENOENT). The metadata storm only emerged at scale — many jobs, many Python imports, all
at startup simultaneously.

Fix: Library removed from all beforeScript hooks and deleted from the repository entirely (May 2026).
The conda activation ENOENT problem was solved instead via a bash function defined in setup.sh that
intercepts conda info --json and returns hardcoded JSON, eliminating all Python imports from the
activation path — this approach survives conda update because it lives in a tracked file outside
conda's install tree. UNCHECKED_HASH .pyc recompilation (bin/recompile_pyc.sh, also tracked in git)
eliminates source-file stat() calls at import time across all conda envs.


Incident 3 — BeeGFS write overhead: Nextflow trace/timeline/report
-------------------------------------------------------------------
What happened: Nextflow's built-in timeline, report, and trace were enabled (default). When enabled,
Nextflow injects polling functions (nxf_mem_watch(), nxf_trace_linux(), nxf_stat()) into every
.command.run script. Each running job maintains a background loop that writes .command.trace metrics
to BeeGFS every second.

With 80 concurrent jobs: 80 BeeGFS writes per second of pure overhead, continuous throughout the
run. This is on top of all the legitimate I/O from databases, FASTQs, and assembly intermediates.

Fix: All three disabled in nextflow.config at HPC admin request. dag remains enabled (static graph
generated once at end, no per-task overhead).


Incident 4 — Wrong memory reservations: LSF perTaskReserve/perJobMemLimit
--------------------------------------------------------------------------
What happened: Two independent LSF configuration bugs caused memory reservations to be wrong:

1. DTU HPC's lsf.conf sets LSB_JOB_MEMLIMIT=Y. Nextflow auto-detects this and sets
   perJobMemLimit = true, which disables -M (per-slot kill limit) division by CPUs. Result: jobs
   requested a kill limit of e.g. 40 GB total for a 16-CPU job — LSF saw this as a 40 GB/slot
   request, blocking scheduling on 128 GB nodes.

2. rusage[mem=X] (the actual reservation) was not divided by CPUs because perTaskReserve was not
   set (DTU HPC does not set RESOURCE_RESERVE_PER_TASK in lsf.conf). Nextflow therefore submitted
   full-job memory as per-slot memory, generating duplicate conflicting -R strings in the job
   submission.

Effect: jobs either PEND indefinitely ("Resource (mem) limit exceeded"), or grab far more slots than
needed, inflating queue pressure and displacing other users' jobs.

Fix: Two-part: (1) setup.sh shadows /lsf/conf/lsf.conf with LSB_JOB_MEMLIMIT=N so Nextflow sees a
standard configuration; (2) perTaskReserve = true set explicitly in conf/lsf.config so rusage is
divided by CPUs. Result: single clean -R "select[mem>=<total>] rusage[mem=<per-slot>]" per job.


Incident 5 — BeeGFS burst traffic: scratch=true on database-heavy processes
----------------------------------------------------------------------------
What happened: FASTP, KRAKEN2, and BAKTA had scratch = true. Nextflow's scratch mode rsyncs the
process work directory to /tmp before execution. However: database paths are passed as Nextflow path
inputs pointing to directories — Nextflow symlinks directories rather than rsyncing them, so the
17 GB Kraken2 DB, 17 GB KmerFinder DB, and 72 GB Bakta DB were always read over InfiniBand
regardless. Only the small input files (FASTQs, FASTAs) were actually rsynced.

The rsync of input files created unnecessary BeeGFS read traffic at job startup (up to 30 FASTP
jobs × 2×7.5 GB FASTQs = 450 GB/burst). For BAKTA, the 72 GB DB was too large to copy to /tmp
anyway — scratch = true provided no benefit and the rsync overhead was pure waste.

Fix: scratch = true removed for FASTP, KRAKEN2, BAKTA, and KRAKEN2_LONG. Retained only for
UNICYCLER (SPAdes writes GB of k-mer graph intermediates that genuinely benefit from local /tmp)
and BUSCO (augustus per-gene intermediates). maxForks caps added to bound concurrent InfiniBand
database reads.


Incident 6 — Unicycler/SPAdes: stale checkpoint reuse and triggered rerun
--------------------------------------------------------------------------
What happened (correctness issue leading to a cluster-stress rerun):

SPAdes (the assembler underneath Unicycler) uses k-mer graph checkpoints stored in subdirectories
spades_assembly/K21/, K27/, K33/, etc. When scratch = true, these are written to a node-local /tmp
path. If a job is killed mid-assembly (e.g. by LSF walltime or by the HPC admin), these partial
checkpoint directories remain on disk in /tmp on that node.

If a subsequent Unicycler job for a different sample happens to land on the same node AND Nextflow
assigns it the same random scratch subdirectory path (which is based on the work directory hash),
SPAdes finds existing checkpoints and silently resumes from them — building the new sample's
assembly on top of a different sample's graph topology. The resulting FASTA has the correct read
depths for the new sample but the wrong contig structure. This produces a chimeric assembly that
is difficult to detect from metrics alone.

This bug was triggered during the 218-sample Vibrio Galathea3 run. The chimeric assemblies went
undetected initially because Unicycler reported plausible N50 and contig count values. The problem
was only suspected when QUAST metrics appeared inconsistent with Unicycler log output — which turned
out to be a separate parser bug, not actual data corruption. The assemblies were confirmed
reproducible (rerun = original for all 218 samples), ruling out chimeric assemblies.

However, the suspicion alone caused a full 218-sample rerun to be submitted, which placed
significant load on the cluster and contributed to the fairshare depletion that drew HPC admin
attention.

Root cause of the stale checkpoint bug: beforeScript cannot fix this because it fires before
Nextflow's cd $NXF_SCRATCH — any rm there targets the NFS work dir, not the scratch dir where
spades_assembly/ lives. The fix must be inside the script block itself.

Fix: rm -rf spades_assembly/ 2>/dev/null || true added as the first line of the UNICYCLER script
block in modules/local/unicycler/main.nf. This unconditionally clears any stale SPAdes state at
the start of each job, before Unicycler launches. Additionally, maxForks = 15 and
clusterOptions = '-R "order[-slots]"' were added to reduce the probability of SPAdes jobs
co-locating on the same node (reducing both CS pressure and checkpoint collision risk). Note:
maxForks was initially set to 6 as an emergency fix but raised to 15 — at 6, a 218-sample run
would take ~73h assembly time, right at the 72h wall time limit. At 15 with order[-slots],
each node runs at most 2–3 concurrent SPAdes jobs, which is safe.

Compounding factor — SPAdes CS storms: SPAdes spawns many short-lived subprocesses per k-mer graph
stage (fork/exec/wait cycles for each k-mer size K21→K127). With the original configuration
(no maxForks, process_high label = 16 declared CPUs, queueSize = 150), many SPAdes jobs could
co-locate on the same node, generating context-switch bursts severe enough to make nodes
unreachable. This was the same mechanism as the FastQC incident but from subprocess spawning
rather than JVM thread inflation.

Note on cpus = 2 for Unicycler: the current setting was chosen based on empirical trace data from
this dataset (33 Vibrio samples, ~3.5–5 Mb genomes, clean paired-end Illumina reads). SPAdes
averaged ~1 core and peaked at 3.3 GB on these small genomes, because most of SPAdes' runtime is
spent in sequential graph simplification phases between parallel k-mer counting rounds. At this
genome size, SPAdes does not saturate more than 2 threads in practice.

This is not a general statement about SPAdes: for larger or more complex bacterial genomes (e.g.
Streptomyces at ~8 Mb, or assemblies with high repeat content), SPAdes scales toward 8 threads
and cpus = 2 would be genuinely wrong — wasting wall time without reducing cluster load. For such
genomes, cpus should be raised to 4–8, with maxForks adjusted to keep cpus × maxForks within a
reasonable per-node slot budget (recommended: no more than 20 slots globally committed to Unicycler
at once).


Incident 7 — NFS read-bottlenecking: DeepBGC Pfam database (funcscan)
----------------------------------------------------------------------
What happened: The DeepBGC pipeline (part of nf-core/funcscan's BGC screening) runs hmmscan
against a 2.8 GB Pfam HMM database. Nextflow stages directory inputs as symlinks, not copies —
so even with scratch = true, hmmscan reads the entire Pfam DB from BeeGFS over InfiniBand for
the full duration of every job. With 218 samples running concurrently and no maxForks limit,
this created sustained multi-hundred-GB InfiniBand read pressure shared across the cluster.

A second problem compounded this: funcscan's default CPU allocation for DEEPBGC_PIPELINE was
1 CPU. HMMER's hmmscan auto-detects available cores and runs single-threaded when only 1 is
declared. For assemblies with 80+ contigs, single-threaded hmmscan took 3–5h per contig,
causing jobs to exceed the 24h wall time and retry. Retries added more NFS reads and more
InfiniBand pressure on top of the already-running jobs.

Root cause: Nextflow's scratch mechanism only copies regular files, not directories — it always
symlinks directory inputs back to BeeGFS. This is a subtle but important distinction: scratch =
true does not protect against NFS load for database inputs, only for output intermediates.

Fix (conf/funcscan_patches/deepbgc_pipeline_main.nf):
- An explicit rsync -aL (dereferencing symlinks inside the DB directory) copies the 2.8 GB DB
  to /tmp/josne/deepbgc_db/ at the start of each job, then sets DEEPBGC_DOWNLOADS_DIR to that
  local path. From that point, hmmscan reads entirely from local disk.
- rsync is idempotent: if another job already ran on the same node, subsequent rsyncs complete
  in seconds (only changed files transferred).
- maxForks = 10 caps how many initial rsyncs run simultaneously, bounding peak InfiniBand load
  to 10 × 2.8 GB = 28 GB (vs. potentially 218 × 2.8 GB = 610 GB uncapped).
- CPU raised from 1 → 5: observed performance plateaus at ~5 effective HMMER threads for
  bacterial contig sizes; 2× throughput gain over the default, no extra node cost vs. 10 CPUs.
- Memory corrected from 16 GB → 4 GB: peak observed was 280–400 MB (HMMER streams the DB from
  disk and does not cache it in RAM).
